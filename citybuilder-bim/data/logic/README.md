# Construction logic library (Track A, Phase 3)

Recipes describe what a particular installation needs, including the work that has no BIM element. They sit above the step libraries and mapping rules:

```
IFC element --mapping rule--> chain of library steps       (what the model shows)
IFC element --recipe--------> chain of steps + virtual steps (what the work needs)
```

| Layer | File | Role |
| --- | --- | --- |
| Step library | `data/sectors/<sector>/step_library.json` | atoms (`STR-SLAB-POUR`) and the virtual atoms (`GEN-SURVEY-SETOUT`) |
| Mapping rules | `data/sectors/<sector>/mapping_rules.json` | element to flat step chain, mechanical and per element |
| Recipe | `data/logic/recipes/<sector>/<rec_id>.json` | molecule: steps bound to elements, virtual steps, ordering logic, hold points, prerequisites |
| Rationale | `data/logic/recipes/<sector>/<rec_id>.md` | why, sequence narrative, pitfalls, reference names |
| Index | `data/logic/index.json` | generated by the pipeline from the recipe files; the table below is the hand-made equivalent |

Counts: 14 industrial, 10 civil, 10 healthcare and 2 all-sector recipes (36 in total), each with a sibling `.md`. Validate with `python3 tools/validate_schemas.py recipe data/logic/recipes/*/*.json`.

## How a recipe works

* **`ref` steps** are library step ids. Without `virtual` they are bound to the BIM element(s) that produce them (`from_element`: `self`, `foundation`, `host`, `system`, `zone`). The mapper already creates those tasks; the recipe says which of them belong to the installation and in what order.
* **Virtual steps** (`virtual: true`) have no element. The pipeline creates a virtual task (`element_guid: null`) when the recipe is applied to a zone. Library virtual steps are tagged `virtual`; every recipe virtual step has a `marker` for the zone marker kit.
* **Order**: steps run in the listed order (FS to the previous step). A step with `parallel_with` starts together with that step (SS) and is not part of the main chain: the step after it follows the step before it. Use `logic` for any other link (a 7 day cure lag, an FF link, a link that skips a step) and `lag_days` or `duration_days` on the step for time-driven items.
* **Hold points** (`hold_point`) are inspection types that must pass after the step, using the library vocabulary: structural, mechanical, electrical, plumbing, fire, medical_gas, icra, pavement, geotechnical, welding, pressure_test.
* **Optional steps** (`optional: true`) are only included when the planner opts in.
* **Nesting**: a step may be `{"recipe": "rec_crane_lift_heavy", "key": "lift"}`. `rec_vertical_vessel` and `rec_turbine_on_pedestal` use it for the lift.
* **`applies_to`** keys are alternatives (OR across keys) in the mapping rules vocabulary: `ifc_class`, `predefined_type`, `name_regex`, `properties`, `zone_tags_any`, plus `visual_kit` and free-text `keywords` for the matcher.
* **`prerequisites`**: `equipment` uses the scenario equipment types (tower_crane, mobile_crane, crawler_crane, excavator, concrete_pump, piling_rig, paver, lift); `site` strings such as `access_road`, `laydown>=3`, `crane_reach`; `permits`; `information` (drawings, lift plans, vendor data).

## Attaching recipes in mapping rules

A rule may carry `recipe: "rec_..."` next to its `steps` (or alone). The pipeline expands the recipe **once per matched element (the anchor)**, so the choice of anchor decides how many tasks appear. The sector rules follow these conventions:

* **One anchor per installation, not per part.** Equipment recipes sit on the equipment rule (module, tank, pump, transformer, turbine, exchanger, vessel); room recipes sit on one representative element per room (one ceiling per operating room or pressure room, never every partition); linear runs sit on the first segment of a run or the first girder of a span; ICRA containment sits on the slabs the zone rule already uses.
* **Each recipe is attached to one rule class**, so the anchor's own steps (the rule's `steps`) are known. A recipe step the anchor naturally carries is reused (same element and step) and is not duplicated. Other BIM-bound steps are marked `optional` by the data build because the model already produces them with other elements; opt in per zone from the game or the API. Virtual steps are always created.
* **`from_element: zone`** creates a zone-level virtual task, `foundation` binds to the footing or slab under the anchor, `system` to every element of the anchor's system. The sector recipes keep `zone` for room recipes and use `self` otherwise; opt-in steps that would otherwise multiply tasks carry a fixed `quantity`.
* **The recipe is the authority on local order, the library only holds cross-element logic.** Library predecessor rules on virtual steps never contradict a recipe: recipes list steps in non-decreasing library phase order (paperwork, permits, lift plans and crane mobilisation first, as-builts and tests at their phase) and use `parallel_with` only for partners in the same or an earlier phase. Cumulative gates would otherwise report `gate_cycle` gaps. A `logic` link may not run from a later phase back to an earlier one.
* **Time-driven virtual steps still occupy a crew slot** in the baseline scheduler (curing watch, dewatering run, vendor attendance), so durations are short and a curing watch is only created when its pour is.

Current attachments (synthetic projects, standard level): industrial 14 rules with recipes and 257 virtual tasks, civil 9 and 167, healthcare 9 and 161.

## Marker vocabulary

`survey` (set-out, locate, as-built, anchor survey), `dewatering`, `shoring`, `scaffold`, `lift_plan`, `crane` (mobilise and load test), `permit` (permits, temporary works check, vendor attendance), `test` (hydrotest, pre-commissioning, curing watch, punch). The marker kit itself is a separate deliverable; the ids are the contract.

## Authoring guide

1. Pick the installation and write the `applies_to` matchers first: a visual kit, an IFC class with a name or property, a zone tag. Add `keywords` people would search for.
2. List the physical sequence from the first site activity (survey, locate, permit) to the last (clearance, handover). Mix BIM-bound steps with virtual steps; use only ids from the sector library (or `all` recipes with `GEN-*` ids that exist in every library).
3. Use `parallel_with` for time-driven support (dewatering, curing) and `logic` with `lag_days` for cure or settlement delays. Do not repeat the plain chain in `logic`.
4. Put a `hold_point` on every inspection the real job needs and name the paperwork (permits, lift plan, temporary works check) as virtual steps rather than prose.
5. Fill `prerequisites` so the planner can see missing cranes, access or permits before starting.
6. Write the `.md`: rationale, sequence narrative, pitfalls and references. References are general standard or guidance names; do not invent clause numbers.
7. Run the cross-check: every `ref` exists in the library, every `logic` end names a step key or ref, nested recipes exist, there are no cycles, hold-point types and equipment types are in the vocabulary.
